# SECURITY_AUDIT.md

## 1. Executive Summary
This audit reviews the implementation of the AppBlock PIN Vault against its stated security model of providing "behavioral friction" against impulsive access to an AppBlock PIN. The application implements the core security properties: offline PIN generation, Android Keystore encryption, and persistent time-based recovery delays. However, several limitations inherent to local device constraints and the Android application lifecycle were identified and addressed.

## 2. Architecture Reviewed
The architecture isolates sensitive cryptographic operations inside native Kotlin using Android Keystore, bridging to Flutter via MethodChannels. The Flutter layer manages UI and recovery timing logic. The separation of concerns is correctly maintained, and cryptographic logic resides in the native layer.

## 3. Cryptographic Review
### Android Keystore
- The AES key is generated inside `AndroidKeyStore` (`KeyProperties.KEY_ALGORITHM_AES`).
- The key is not exported and is never serialized to `SharedPreferences` or returned to Dart.
- The `SecurityService.kt` accesses the key alias across app restarts.
### AES-GCM
- `AES/GCM/NoPadding` is utilized.
- A fresh random IV is generated by `Cipher.init` on every encryption pass and stored alongside the ciphertext.
- GCM authentication tags are generated using a 128-bit tag length (`GCM_TAG_LENGTH = 128`).
- Tag authentication failures trigger an `AEADBadTagException` natively, gracefully causing decryption to fail and returning `null` over the MethodChannel.

## 4. PIN Lifecycle Review
The plaintext PIN exists temporarily in the Dart memory heap during generation, initial setup, PIN reveal, and rotation.
- **Leakage check**: The PIN is not written to `SharedPreferences`, SQLite, files, logs, or analytics.
- **Exceptions**: `NativeSecurityService.dart` handles exceptions gracefully without interpolating the PIN into stack traces or logs.
- **Clipboard**: The PIN is copied to the clipboard only upon explicit user action and is scheduled to clear.

## 5. Storage Review
`SharedPreferences` is used for application state.
- `pin_ciphertext`: Encrypted payload.
- `pin_iv`: Initialization vector.
- `recovery_started_at`, `recovery_available_at`, `last_observed_time`: Absolute timestamps used for timing.
- No sensitive key material or plaintext PIN is persisted.

## 6. Recovery State Machine Review
Transitions operate as designed: `locked` → `recoveryPending` → `challengeReady` → `revealReady` → `pinRevealed`.
- Illegal transitions are protected by timing checks.
- If the application restarts, `verifyRecoveryState` reconstructs the active state based on the stored absolute timestamps.

## 7. Timing Review
The application relies exclusively on `recoveryAvailableAt`. The UI countdown timer is strictly presentation logic.
- Killing, restarting, or rebooting the device maintains the original deadline.
- Changing the recovery delay setting applies only to future requests and leaves any active pending recovery unchanged.

## 8. Clock Manipulation Review
Anti-tampering logic is implemented using a `lastObservedTime` tracking mechanism and `elapsedRealtime`.
- If `DateTime.now()` is earlier than `lastObservedTime` by more than 5 minutes, the app detects an obvious clock rollback and suspends recovery (`timeAnomalyDetected`).
- **Limitation**: This detects obvious backward manipulation. It does not prevent forward manipulation if the user reboots the device and changes the wall clock. If the user corrects their clock back to network-time, the recovery request will resume from where it left off.

## 9. PIN Rotation Review
PIN rotation is atomic at the storage level.
- The old encrypted PIN and IV in `SharedPreferences` are only overwritten via an atomic `.apply()` transaction if the new encryption completes successfully.
- If the app crashes, the encryption fails, or the persistence fails, the old PIN remains intact and recoverable.
- The temporary plaintext new PIN is held in volatile Dart memory and perishes on restart.

## 10. Clipboard Review
The PIN is copied to the clipboard strictly upon manual action.
- A 60-second Timer clears the clipboard text, and the app clears it when navigating away from the Reveal Screen.
- **Limitation**: If the user forcefully kills the app via the Android app switcher before 60 seconds elapse, the Flutter Timer perishes, and the PIN remains in the clipboard indefinitely, subject to OS behavior.

## 11. Android Lifecycle Review
- When backgrounded, Dart memory is maintained. The UI continues to show the PIN if already revealed.
- When destroyed/killed, all memory is wiped.
- When restarted, the app resets to the `locked` state safely.

## 12. Backup Review
- **Android Auto Backup**: Android automatically backs up `SharedPreferences` to Google Drive.
- **Keystore**: Hardware-backed Keystore keys are strictly tied to the specific physical device and are not backed up.
- **Impact**: If a user restores their device from a backup onto a new phone, the app will recover the ciphertext but fail to decrypt it because the key is missing. The PIN is permanently lost.

## 13. Uninstall/Reinstall Review
- Uninstalling the application destroys the `SharedPreferences` and wipes the hardware `AndroidKeyStore` alias.
- Reinstalling the application will result in a fresh state. Even if Auto Backup restores the ciphertext, the decryption key is permanently destroyed. The old PIN is irretrievable.

## 14. Debug/Release Review
- ProGuard/R8 applies standard Flutter obfuscations.
- No dangerous permissions (e.g., `INTERNET`) are requested or required by the release manifest.

## 15. Threat Model
| Threat | Status | Description |
|---|---|---|
| A. Curious user opening vault normally | **Protected** | Requires explicit setup and configured time delay. |
| B. User attempting impulsive recovery | **Protected** | Must wait the full duration (e.g. 24h) and pass the explicit challenge screen. |
| C. User killing/restarting the app | **Protected** | Absolute timestamps defeat memory-based timer bypasses. |
| D. User changing system time | **Partially Protected** | Rollbacks are detected (`timeAnomalyDetected`), but offline-only restriction prevents blocking all forward manipulation. |
| E. User inspecting application files | **Protected** | SharedPreferences only contains AES-GCM ciphertext. Keystore protects the key. |
| F. User using Android debugging tools | **Partially Protected** | A rooted device owner can extract memory or manipulate SharedPreferences, but hardware Keystore typically prevents key extraction. |
| G. User uninstalling the app | **Protected (Failsafe)** | Uninstall securely destroys the Keystore key. The PIN is permanently unrecoverable. |

## 18. Overall Security Limitations
The AppBlock PIN Vault provides behavioral friction. However, it is structurally limited by the Android platform: because it requires zero internet access to function, it cannot rely on cryptographic network time protocols (NTP). Consequently, a sufficiently motivated device owner with full system access can bypass application-level time restrictions across reboots. The cryptographic implementation (Android Keystore + AES-GCM) is correctly integrated and provides protection against offline file extraction.

## 19. Remediation Summary
The security remediation sprint implemented:
1. Native `FLAG_SECURE` toggling for the `RevealScreen` to prevent visual leakage.
2. Advanced clipboard lifecycle management utilizing Flutter's `AppLifecycleState.resumed` and component `dispose` to clear the clipboard reliably.
3. Monotonic timing (`elapsedRealtime`) verification to enforce countdowns during a single boot session, supplementing the persisted wall-clock timestamps.
